## 1. 문제 정의와 처음 계획

### 1-1. 풀려는 문제

- 쇼츠는 "나중에 보려고 저장"해도 제목·썸네일밖에 안 남아서 **내용으로 다시 찾을 수 없다.**
- 특히 요리·정보성 쇼츠는 "그 재료 얼마나 넣었지?", "몇 초에 그 장면 나오지?" 같은 **시점 단위 질문**이 많다.
- 목표: 저장 시점에 영상을 **말(음성) · 글(화면 자막) · 그림(장면)** 세 정보원으로 이해해 두고,
  검색 시 **어느 영상의 몇 초**인지까지 답한다.

### 1-2. 계획 단계에서 정한 원칙 (마스터 문서 "확정본")

팀 4명(A·B·C·D)이 나눠 만들기 위해, 구현 전에 파이프라인을 **13개 단계**로 쪼개고 단계마다
입출력 모양을 고정한 "마스터 문서"를 먼저 썼습니다. 그때 정한 핵심 원칙:

| # | 원칙 | 이유 |
| --- | --- | --- |
| 1 | **서버는 유튜브에 한 번도 접속하지 않는다.** 화면과 소리는 브라우저(확장)에서 뽑아 올린다 | yt-dlp 류 다운로드는 약관·차단 문제. 사용자가 실제로 보고 있는 화면을 캡처하는 건 합법적이고 안정적 |

| 3 | **모든 모델 단계는 "demo 대체품 / 진짜 모델" 두 백엔드를 같은 인터페이스로** 갖는다 | Gemini로 먼저 전 구간을 잇고, 담당자가 진짜 모델을 붙일 때 `.env` 한 줄만 바꾸면 되게 |

## 2. 전체 구조

```
크롬 확장 (Side Panel)
   │ ① 저장 버튼 → 메타데이터 접수 (POST /api/videos)
   │ ② 영상을 재생하며 프레임(0.5초마다, 540×960 JPEG) + 오디오(16kHz wav) 추출
   │    → 서버로 업로드 (POST /api/videos/{id}/media)            ★ 핵심 — 서버는 유튜브를 모름
   ▼
API 서버 (FastAPI) ── 작업 큐 (asyncio) ── Worker
                                            ├ 단계 4  음성 받아적기     (Gemini │ faster-whisper / WhisperX)
                                            ├ 단계 5  화면 글자 읽기    (Gemini 격자 │ EasyOCR)
                                            ├ 단계 6  장면 설명         (Gemini, 6장→격자 1장, 영상당 ≤3회)
                                            ├ 단계 7  4초 장면 카드 합치기
                                            ├ 단계 8  글 좌표 + 그림 좌표 → Qdrant  (Gemini │ BGE-M3 + SigLIP2)
                                            └ 단계 9  전체 요약 (Gemini)
   │ 확장이 3초마다 진행률 확인 (20 → 40 → 65 → 85 → 95 → 100%)
   ▼
검색: 의도 분류 → 하이브리드(글 좌표·정확한 단어·그림 좌표) + user_id 필터 → 인접 장면 중복 제거
      → RAG 답변 (Gemini) → 클릭하면 유튜브 영상을 그 초로 이동 (1.5초 일찍)
```

### 저장소 구성 (데모용으로 줄인 것)

| 마스터 문서 | 데모 | 바꾸는 법 |
| --- | --- | --- |
| PostgreSQL | SQLite `data/vault.db` (videos, segments, condition_runs, playlists) | `db.py` 함수 시그니처 유지하며 교체 |
| Redis 작업 큐 | 서버 안 `asyncio.Queue` | `worker.enqueue()` 만 교체 |
| Qdrant Cloud | 로컬 파일 모드 `data/qdrant/` | `.env` 에 `QDRANT_URL` |
| 로그인 | `X-User-Id` 헤더 (확장이 만든 uuid) | `main.current_user()` 교체 |

## 3. 파이프라인 단계별 구현

### 단계 1~2 · 브라우저 추출 (확장, `content.js`)

- 저장 버튼을 누르면 `<video>`를 0초로 되감고 재생하면서 `setInterval`로 0.5초마다 `canvas.drawImage` → JPEG blob.
- **중복 프레임 제거**: 축소 캔버스(tiny)로 이전 프레임과 픽셀 차이를 재서 임계값(2%) 이하면 버림. 정지 화면이 많은 쇼츠에서 업로드량이 크게 줄어듦.
- **오디오**: `video.captureStream()` → `MediaRecorder`(webm/opus) → 끝나면 `OfflineAudioContext`로 **16kHz 모노 wav로 변환**해서 올림. 덕분에 서버에 ffmpeg가 필요 없음.
- 파일 이름이 곧 시각: `00022000.jpg` = 22.0초. 이 규약 하나로 이후 모든 단계가 시간을 맞춤.
- 제약: **실시간 재생 추출**이라 60초 영상이면 60초 걸리고 그 탭에 머물러야 함. (진행바로 표시)

### 단계 3 · 접수 + 작업 큐 (`main.py`, `worker.py`)

- `POST /api/videos` (메타데이터) → `POST /api/videos/{id}/media` (프레임+오디오 multipart) → 큐 등록.
- Worker가 단계 4~9를 순서대로 돌리며 `db.set_status()`로 진행 상태를 남기고, 확장은 3초마다 폴링.
- 실패하면 상태를 `failed` + 에러 메시지로 기록해 UI에 그대로 보임.

### 단계 4 · 음성 받아적기 (`transcribe.py`) — 3개 백엔드, 같은 출력 `[{start, end, text, words?}]`

| 백엔드 | 동작 |
| --- | --- |
| `gemini` (기본) | wav를 Gemini에 보내 구조화 출력(pydantic)으로 `[{start, end, text}]` 받음. 설치 없이 바로 됨 |
| `faster-whisper` | CTranslate2 Whisper `small`, `word_timestamps=True`, VAD 필터. **단어 단위 시각**까지 나옴 |
| `whisperx` | faster-whisper + wav2vec2 강제 정렬. 시각이 가장 정확. **단, Python 3.14 미지원** → import 실패 시 자동으로 faster-whisper로 폴백 |

### 단계 5 · 화면 글자 (`ocr.py`) — 두 방식

- `gemini`: 단계 6 격자 호출에 "칸마다 화면 글자도 적어라"를 끼워 넣어 **추가 호출 0회**로 OCR을 얻음.
- `easyocr`: `Reader(["ko","en"])`로 **모든 프레임**을 읽음. 정확하지만 CPU에서 느림 (아래 실측 참고).

### 단계 6 · 장면 설명 (`caption.py`, `frames.py`)

- 대표 프레임을 고르고 **6장을 격자 한 장**으로 붙여(칸마다 노란 번호) Gemini에 한 번 질문.
  구조화 출력으로 칸별 `{index, on_screen_text, description}`을 받음.
- `MAX_GEMINI_CALLS_PER_VIDEO=3`을 코드에서 강제 → 영상당 최대 18장면 설명.
- 로컬 조건에서도 이 단계만은 Gemini를 씀 (로컬 VLM은 범위 밖).

### 단계 7 · 4초 장면 카드 (`segmenter.py`)

- 영상 길이를 4초 창으로 나누고, 각 창에 겹치는 발화(asr) · 그 창 안 프레임의 OCR · 가장 가까운 격자 칸의 설명(caption) · 대표 프레임 경로를 합침.
- 카드 모양 (마스터 문서 견본 그대로):
  ```json
  {"segment_id": "vid_001_seg_006", "start_time": 22.4, "end_time": 26.4,
   "asr_text": "이제 감자를 넣어줍니다", "ocr_text": "감자 300g",
   "caption": "손질된 감자를 프라이팬에 넣는 모습", "frame_path": "frames/00022000.jpg"}
  ```

### 단계 8 · 좌표(임베딩) → Qdrant (`embedder.py`, `image_embedder.py`, `vectors.py`)

- **글 좌표**: 카드의 `제목 + asr + ocr + caption`을 한 문장으로 만들어 임베딩.
  `gemini-embedding-001`(768차원) 또는 `BAAI/bge-m3`(1024차원).
- **그림 좌표**: 대표 프레임을 `SigLIP2-base`(768차원)로 임베딩. 검색어도 같은 모델의 텍스트 타워로 임베딩해 **글 ↔ 그림 교차 검색**.
- Qdrant 컬렉션은 `text` / `image` **named vector** 두 개, COSINE. 포인트 payload에 `user_id`, `video_id`, 카드 내용.
- 모든 검색은 `user_id` filter를 강제 (`tools/test_user_isolation.py`로 검증).

### 단계 9 · 전체 요약 (`summarizer.py`)

- 카드 전부를 Gemini에 주고 `{headline, keywords, steps[{time, label}]}` 구조화 출력. 카드 상단 한 줄과 "주요 단계" 시각 버튼에 씀.

### 단계 11~13 · Side Panel, 검색, 시점 이동

- **검색 (`search.py`)** — 아래 4장.
- **시점 이동**: 결과의 `▶ 00:22` 클릭 → `content.js`가 `video.currentTime = t − 1.5`. 다른 쇼츠를 보고 있으면 그 영상으로 옮긴 뒤 이동, 실패하면 새 탭 폴백.
- **삭제**: 표(SQLite) · 창고(Qdrant, 모든 조건 컬렉션) · 이미지(디스크) 3곳에서 지움.

## 4. 검색 — 하이브리드 + 의도 분류 + RAG

### 4-1. 검색어 성격에 따라 정보원 비중을 바꿈

```python
WEIGHTS = {                 # (글 좌표, 정확한 단어, 그림 좌표)
    "speech":  (0.5, 0.3, 0.2),   # "감자 언제 넣어?"
    "visual":  (0.3, 0.1, 0.6),   # "빨간 냄비 나오는 장면"
    "lexical": (0.3, 0.5, 0.2),   # "300g", "2큰술"
}
```

- 규칙 기반 분류: 수량 정규식(`\d+\s*(g|ml|큰술…)`) → lexical / 색·그릇·냄비 등 시각 단어 → visual / 그 외 → speech.
- 그림 좌표가 없는 조건(Gemini)에서는 그 몫을 나머지 둘에 비례 배분.

### 4-2. 점수 합치기

1. 글 좌표로 Qdrant top-40, 그림 좌표로 top-40 (있을 때).
2. 각각 min-max 정규화 → `score_dense`, `score_image`.
3. `score_lexical` = 검색어 토큰이 카드 텍스트에 정확히 몇 개 들어 있는지 비율.
4. `score = w_dense·dense + w_lexical·lexical + w_image·image`.
5. 응답에 세 점수를 **따로** 실어 보냄 → "정보원별 기여도" 실험은 이 값을 끄고 켜며 잼.

### 4-3. 의도 분류 → 결과 형태

| 의도 | 판단 | 결과 |
| --- | --- | --- |
| `scene` (기본) | "언제·부분·몇 초·타이밍" | 장면 카드 top-k (인접 4초 카드는 하나로 합침) |
| `video` | "그 영상 찾아줘/있어?" | 영상 단위로 묶어 보여줌 |
| `summary` | "요약·정리·재료·순서" | 장면을 넉넉히(≥10) 모아 목록형 답변 |

### 4-4. RAG 답변

- 찾은 장면 텍스트만 근거로 Gemini(`flash-lite`)에게 세 문장 이내 한국어 답. **"장면에 없는 내용은 지어내지 마, 모르면 확인되지 않는다고 해"**를 프롬프트에 명시. 시점 질문이면 초를 같이 말하게 함.

## 5. 모델 정리 — 각각 어떤 역할인가

### 5-1. Gemini 쪽 (demo 기본 조건 `gemini`)

| 역할 | 모델 | 쓰이는 곳 |
| --- | --- | --- |
| 격자 캡션 + OCR, 음성 받아적기 | `gemini-3.5-flash` (`CAPTION_MODEL`) | 단계 4·5·6 — 영상당 ≤3+1회 |
| 요약, RAG 답변 | `gemini-3.5-flash-lite` (`ANSWER_MODEL`) | 단계 9, 검색 답변 |
| 글 좌표 | `gemini-embedding-001` 768차원 | 단계 8 |
| 그림 좌표 | 없음 | — |

### 5-2. 로컬 쪽 (조건 `local`) — 4개 모델, 전부 CPU에서 실제 동작 확인 (2026-09-02)

| 단계 | 모델 | 역할 | 확인 결과 |
| --- | --- | --- | --- |
| 4 음성 | **faster-whisper `small`** (CTranslate2, int8) | 한국어 음성 → 문장 + **단어 단위 시각** | 81초 오디오 → 41문장, 단어 시각 포함 |
| 5 자막 | **EasyOCR** ko+en | 프레임의 한글·영문 자막, 워터마크 읽기 | 10프레임 전부 인식 (자막·채널명까지) |
| 8 글 좌표 | **BGE-M3** (`BAAI/bge-m3`, 1024차원) | 카드 텍스트 ↔ 검색어 의미 유사도 | "감자 언제 넣어?" ↔ "감자를 넣어줍니다" 0.817 / 무관 문장 0.391 |
| 8 그림 좌표 | **SigLIP2-base** (`google/siglip2-base-patch16-224`, 768차원) | 프레임 ↔ 검색어 교차 검색. 요리 도메인 LoRA 자리(`SIGLIP_ADAPTER`) 마련 | 8프레임 8.9초, 자막 있는 프레임에서 "text on screen" 최고점 |
| 6 장면 설명 | (Gemini 그대로) | 로컬 VLM은 범위 밖 | — |

가중치 다운로드 합계 약 6.3GB (BGE-M3 4.3GB, SigLIP2 1.4GB, whisper 0.46GB, EasyOCR 0.1GB).

## 6. 비교 실험 장치 — Gemini vs 로컬을 "공정하게"

### 6-1. 원리

저장할 때 뽑은 프레임·오디오가 `data/media/<user>/<video_id>/`에 **바이트 그대로 남아 있다.**
비교는 그 파일을 다시 읽어 **백엔드만 바꿔** 돌린다.

```
data/media/<user>/<video_id>/frames/*.jpg + audio      ← 입력 고정
        ├─→ [gemini] Gemini 음성 + Gemini 격자 + Gemini 좌표 → Qdrant shorts_segments
        └─→ [local]  faster-whisper + EasyOCR + BGE-M3 + SigLIP2 → Qdrant shorts_segments__local
```

- 입력이 완전히 같으므로 **차이는 순수하게 모델 차이.** 유튜브에서 매번 새로 받는 방식과 달리 1년 뒤에 돌려도 같은 입력.
- `pipeline/analyze.py`(단계 4~8)를 **제품과 실험이 똑같이 사용.** 실험 숫자가 제품과 다른 코드에서 나오면 의미가 없기 때문.

### 6-2. 구현 포인트

| 장치 | 설명 |
| --- | --- |
| `CONDITIONS` (`config.py`) | 조건 이름 → 백엔드 4개 조합 + 필요한 패키지(대안 목록) |
| `use_condition(name)` | `ContextVar` 기반. 그 블록 안에서만 `backend("asr")` 등이 조건 값을 돌려줌. 스레드/태스크별 독립이라 두 조건을 동시에 돌려도 안 섞임 |
| 조건별 Qdrant 컬렉션 | 좌표 차원이 다르므로(768 vs 1024) `shorts_segments__local`처럼 분리 |
| `condition_runs` 표 | 조건별 결과(카드 수, 단계별 초, 에러)를 저장 → 시연 때 미리 돌려둔 표가 바로 뜸 |
| `POST /api/compare` | 같은 질문을 두 조건으로 검색해 나란히 반환 + 1등 장면의 시각 차이가 4초 이내면 "같은 지점" 판정 |
| `tools/run_condition.py` | 저장된 영상 전부를 조건별로 배치 재분석 (밤에 걸어두는 용도), 진행률 출력 |
| Side Panel `⚗ 비교` 탭 | 조건 카드(패키지 없으면 설치 명령 표시) → 비교표(더 나은 쪽 초록) → 나란히 검색 |

### 6-3. 실측 결과 — 영상 `_pbcDuN2G2I` (81초, 163프레임, CPU 노트북 16GB)

| --- | :---: | :---: |

## 7. 개발 중 부딪힌 문제와 해결

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| WhisperX 설치 불가 | 모든 배포판이 Python `<3.14` 요구, 팀원 환경은 3.14 | WhisperX 내부 엔진인 faster-whisper 백엔드 추가. `ASR_BACKEND=whisperx`여도 import 실패 시 자동 폴백. `requires`를 "대안 목록"으로 바꿔 둘 중 하나만 있으면 준비 완료로 판정 |
| EasyOCR 첫 실행에 서버가 죽음 | 다운로드 진행바의 `█`를 한글 윈도우 콘솔(cp949)이 못 찍어 `UnicodeEncodeError` | `Reader(verbose=False)` |
| whisper `mkl_malloc` 실패 | 로컬 모델 3개를 동시에 띄워 RAM 부족 (16GB 중 여유 2.6GB) | 순차 실행. 배치 돌릴 땐 브라우저 닫기 안내 |
| Gemini 503 | 최신 모델이 붐빌 때 구글 쪽 일시 과부하 (키 문제 아님) | `tools/check_models.py`로 그날 잘 도는 모델 고르기, 설정으로 모델 교체 |
| 확장 원인불명 버그 | 다른 유튜브 확장과 DOM 충돌 | 개발 전용 크롬 프로필, 다른 확장 전부 끄기 |
| 로컬 Qdrant 잠금 충돌 | 파일 모드는 프로세스 하나만 붙음 (`--reload`로 두 번 뜸) | `--reload` 금지, 배치 도구는 직접 붙지 않고 서버 API 경유 |
| 프레임마다 Gemini 호출 시 비용 폭발 | 영상당 120회 | 6장 격자 + 영상당 3회 상한을 코드로 강제 |
| `run_condition`이 몇 분간 무출력 | 완료 때만 출력 | 상태가 바뀔 때마다 %와 경과 초 출력 |

## 10. 현재 상태와 다음 계획

**지금 되는 것**: 저장 → 분석 → 검색 → 시점 이동 전 구간이 Gemini 조건으로 동작. 로컬 조건 4개 모델 전부 CPU에서 돌아가고 비교표까지 나옴.

**바로 다음**
1. **OCR 프레임 줄이기** — 0.5초 프레임 163장을 전부 읽을 이유가 없음. 4초 카드당 1~2장(또는 중복 제거 후)만 읽으면 OCR 시간 1/4~1/8 예상. 로컬 총 시간의 66%가 여기.
2. **GPU 한 줄 전환** (`DEVICE=cuda`) 후 로컬 시간 재측정 — 설계상 이 한 줄만 바꾸면 됨.
3. **정보원별 기여도 실험** — `score_dense / lexical / image`를 끄고 켜며 질문 유형별 정답률 측정 (마스터 문서 9장).
4. **시점 정밀도 실험** — Whisper 단어 시각 vs Gemini 문장 시각으로 "▶ 이동"이 정답 장면에 얼마나 가까운지.
5. 영상 수 늘려 재실측 (지금은 2개).

**더 뒤**: PostgreSQL·Redis·Qdrant Cloud·로그인으로 교체 (교체 지점은 이미 함수 경계로 분리), Cloudflare Tunnel로 공용 서버, 요리 도메인 SigLIP LoRA.

## 11. 멘토님께 여쭤보고 싶은 것 (초안)

1. 비교 실험에서 "회수율(카드 수)"을 품질 지표로 쓰는 게 타당한지, 아니면 사람이 매긴 정답 장면 기준 정확도로 가야 하는지.
2. 검색어 성격 분류를 규칙(정규식·단어 목록)으로 한 것을 그대로 두어도 되는지, 작은 분류기로 바꿀 가치가 있는지.
3. 실시간 재생 추출(60초 영상 = 60초)의 UX 한계를 어디까지 받아들일지 — 백그라운드 탭 재생, 배속 재생 등이 캡처 품질에 미치는 영향.
4. 졸업작품 범위에서 로컬 VLM(장면 설명)까지 붙이는 게 의미 있는지, 아니면 그 단계는 Gemini로 고정하고 다른 축에 집중할지.
