# 쇼츠 AI 보관함 — 검색 로직 정리 (멘토링용)

> 이 문서만 읽으면 현재 검색이 어떻게 도는지 알 수 있게 쓴 자료입니다.
> 코드는 아직 하나도 고치지 않았고, **현재 상태 그대로**를 적었습니다.

---

## 0. 한 줄 요약

사용자가 질문을 넣으면 → **질문을 3가지 성격 중 하나로 규칙 기반 분류**하고 →
그 분류에 딸린 **고정 가중치 3개**로 **3가지 신호(의미·단어일치·이미지)** 를 가중합해
장면을 정렬한 뒤 → 상위 장면을 Gemini에 넣어 RAG 답변을 만듭니다.

**분류 기준도, 가중치 숫자도 전부 파이썬 파일에 상수로 박혀 있습니다.**
실험이나 근거로 정해진 값이 아니라 처음에 사람이 감으로 써둔 값입니다.

## 1. 파일 지도 — 어디가 검색 로직인가

| 파일 | 역할 | 검색 관련도 |
| --- | --- | --- |
| `server/search.py` (318줄) | **검색 로직 본체.** 질문 분류 · 가중치 · 신호 합산 · 중복제거 · RAG | ★★★ 여기가 전부 |
| `server/vectors.py` | Qdrant 벡터 검색 호출 + `user_id` 격리 필터 | ★★ 후보를 긁어오는 층 |

| `server/image_embedder.py` | 질문/프레임 → **그림 좌표**(SigLIP2). 기본값 `none`(꺼짐) | ★★ 신호 3의 모델 |

| `extension/sidepanel.js` | 결과 렌더링 (623~624줄에서 가중치를 화면에 표시) | ★ 표시만 |

## 2. 검색 대상이 무엇인가 (색인 단계)

영상 1개를 저장하면 **4초 단위 "장면 카드"** 로 쪼갭니다 (`segmenter.py:70`).

```python
{
  "segment_id": "abc123_seg_007",
  "start_time": 28.0, "end_time": 32.0,
  "asr_text":  "여기서 감자를 넣어주고요",   # 음성 (Whisper 또는 Gemini)
  "ocr_text":  "감자 2개",                  # 화면 글자 (EasyOCR 또는 Gemini)
  "caption":   "빨간 냄비에 감자를 넣는 장면", # 장면 설명 (Gemini)
  "frame_path": "frames/000028.jpg"
}
```

이 카드가 Qdrant에 **좌표 2개를 달고** 들어갑니다 (`vectors.py:104`).

- `text` 벡터 ← `search_text()` 가 만든 한 덩어리 문자열
  `"영상제목. 장면설명. 음성. 화면글자"` (`segmenter.py:122`)
- `image` 벡터 ← 그 구간 대표 프레임 1장을 SigLIP2로 (**기본은 안 만듦**)

> ⚠ **여기가 이미 하나의 설계 결정입니다.** 제목·설명·음성·자막을 **한 문자열로 합쳐서
> 벡터 1개**로 만들기 때문에, "음성에만 있는 말"과 "제목에만 있는 말"을 검색 단계에서
> 구분할 방법이 없습니다. (필드별 벡터를 따로 두는 선택지도 있습니다.)

## 3. 검색 단계 — 팀원이 말한 "3개의 방향"

팀원이 말한 3갈래는 사실 **두 겹**으로 3개입니다. 섞어서 이해하면 헷갈립니다.

### 3-A. 질문의 "성격" 3종 — `classify_query()` (`search.py:38`)

```python
def classify_query(query):
    if QUANTITY_RE.search(query):              # 숫자+단위가 있으면
        return "lexical"                        #   "간장 2큰술", "300g"
    if any(term in query for term in VISUAL_TERMS):  # 시각 단어가 있으면
        return "visual"                         #   "빨간 냄비 나오는 장면"
    return "speech"                             # 나머지 전부
```

판정에 쓰는 사전이 전부 코드에 박혀 있습니다:

```python
VISUAL_TERMS = ("색","보이는","모양","빨간","노란","파란","초록","하얀","검은",
                "그릇","냄비","프라이팬","화면","장면 사진","노릇","그을")   # 15개
QUANTITY_RE  = r"\d+\s*(g|kg|ml|l|개|스푼|큰술|작은술|컵|분|초|인분|%)"
```

- **단 하나의 성격만 고릅니다.** 겹치면 위에서부터 이긴다 = `if` 순서가 곧 우선순위.
  → `"빨간 냄비에 간장 2큰술"` 은 숫자 조건이 먼저라 **`lexical`** 로 잡히고
    "빨간 냄비"라는 시각 정보는 가중치에 **전혀 반영되지 않습니다.**
- `VISUAL_TERMS` 는 요리 도메인 15단어짜리 수작업 사전입니다. "파스타 면 색깔"은 잡히지만
  "노른자 터지는", "김 나는", "갈색으로" 같은 건 안 잡힙니다.

### 3-B. 점수 "신호" 3종과 가중치 — `WEIGHTS` (`search.py:19`)

```python
#                 (글 좌표, 정확한 단어, 그림 좌표)
WEIGHTS = {
    "speech":  (0.5, 0.3, 0.2),   # "감자 언제 넣어?"
    "visual":  (0.3, 0.1, 0.6),   # "빨간 냄비 나오는 장면"
    "lexical": (0.3, 0.5, 0.2),   # "300g", "2큰술"
}
```

최종 점수 = `w_dense·dense + w_lexical·lexical + w_image·image` (`search.py:157`)

| 신호 | 무엇 | 어떤 모델 | 계산 방식 |
| --- | --- | --- | --- |
| **dense** (글 좌표) | 의미가 비슷한가 | Gemini embedding(기본) 또는 **BGE-M3** | 코사인 유사도 → **min-max 정규화** |
| **lexical** (정확한 단어) | 그 단어가 실제로 들어 있나 | **모델 없음. 순수 규칙** | 질문 토큰 중 본문에 들어간 비율 |
| **image** (그림 좌표) | 그림이 비슷한가 | **SigLIP2** (기본 꺼짐) | 코사인 유사도 → min-max 정규화 |

`lexical_score()` 실체 (`search.py:84`) — 여기가 생각보다 단순합니다:

```python
tokens = TOKEN_RE.findall(query)          # 한글 2자↑ / 영문 2자↑ / 숫자+단위
text   = title + caption + asr_text + ocr_text   # 그냥 이어붙임
matched = sum(1 for t in tokens if t in text)     # 단순 부분문자열 포함
return matched / len(tokens)
```

- BM25도, IDF도, 형태소 분석도 없습니다. **`in` 연산 한 줄**입니다.
- 그래서 `"감자"` 는 `"감자칩"`, `"고구마감자탕"` 에도 매칭됩니다.
- 흔한 단어(`"장면"`, `"만들"`)와 희귀 단어(`"수비드"`)가 **똑같은 1점**입니다.
- 제목이 4개 필드에 섞여 들어가므로, **같은 영상의 모든 장면이 제목 매칭 점수를 공유**합니다
  (영상 단위 편향은 생기고 장면 구분에는 도움이 안 됨).

### 3-C. ⚠ 실제로는 지금 "2갈래"만 돕니다

`weights_for()` (`search.py:58`)는 SigLIP2가 꺼져 있으면 **그림 몫을 나머지 둘에 비례 배분**합니다.
`.env.example` 기본값이 `IMAGE_EMBED_BACKEND=none` 이고, `POST /api/search` 는 condition을
받지 않아 **항상 기본 조건(`gemini`)** 으로 돌기 때문에 — 평소 검색 탭에서는 이렇게 됩니다:

| 질문 성격 | 표에 적힌 값 | **실제 적용되는 값** (이미지 꺼짐) |
| --- | --- | --- |
| speech | (0.50, 0.30, 0.20) | **(0.625, 0.375, 0)** |
| visual | (0.30, 0.10, 0.60) | **(0.750, 0.250, 0)** |
| lexical | (0.30, 0.50, 0.20) | **(0.375, 0.625, 0)** |

**의도와 정반대의 일이 벌어집니다.** "빨간 냄비 나오는 장면"(visual)은 그림으로 찾으라고
만든 분기인데, 그림이 꺼지면 **세 분기 중 dense 비중이 가장 높은(0.75)** 케이스가 됩니다.
즉 시각 질문일수록 시각 신호를 못 쓰는 상태로 되돌아갑니다.

SigLIP2/BGE-M3는 지금 **비교 탭(`POST /api/compare`)에서만** 실제로 돕니다 (`main.py:414`).

## 4. 후보를 모으고 정리하는 과정 — `hybrid_search()` (`search.py:103`)

```
질문
 ├─ 텍스트 벡터 검색 → 상위 top_n개          (vectors.search, user_id 필터 필수)
 └─ 이미지 벡터 검색 → 상위 top_n개          (꺼져 있으면 건너뜀)
        ↓
   두 풀을 segment_id로 합집합(_merge)
        ↓
   각 카드에 dense / lexical / image 점수를 붙여 가중합
        ↓
   점수순 정렬 → dedup_adjacent → top_k
```

- `top_n = max(top_k * 8, 40)` — 상위 5개 보여주려고 40개를 긁어옵니다. (하드코딩)
- **min-max 정규화의 부작용**(`search.py:69`): 각 풀에서 **1등은 항상 1.0, 꼴등은 항상 0.0**
  이 됩니다. 절대 유사도가 0.2든 0.9든 1등이면 만점입니다.
  → **관련 없는 질문에도 항상 그럴듯한 1등이 나옵니다.** 임계값(threshold)이 없습니다.
- **합집합의 함정**: 이미지 풀에만 있는 카드는 `dense = 0.0`, 텍스트 풀에만 있는 카드는
  `image = 0.0` 이 됩니다. 한쪽에서만 잡힌 정답이 강하게 깎입니다.
  (이런 융합에 보통 RRF(Reciprocal Rank Fusion)를 씁니다.)
- **스케일 불일치**: dense/image는 *상대* 정규화된 값, lexical은 *절대* 비율(0/0.5/1 같은
  띄엄띄엄한 값)입니다. 성질이 다른 수를 그냥 더하고 있습니다.

### 후처리

- `dedup_adjacent()` (`search.py:166`) — 같은 영상에서 **2초 이상 겹치는** 장면은 1개만.
- `group_by_video()` (`search.py:187`) — 영상 단위 묶음. **상위 5개 고정**, 썸네일은
  `img.youtube.com/vi/{id}/hqdefault.jpg` 하드코딩.
- `seek_time = start - 1.5초` (`SEEK_LEAD_SECONDS`) — 클릭하면 1.5초 일찍 재생.

## 5. 의도(intent) 분기 — 사실상 작동하지 않습니다

`detect_intent()` (`search.py:47`)가 질문을 `video` / `scene` / `summary` 로 나눕니다.
그런데 이 결과가 쓰이는 곳은 **딱 한 군데**입니다 (`search.py:290`):

```python
scene_limit = max(top_k, 10) if intent == "summary" else top_k
```

- `video` 와 `scene` 은 **완전히 동일한 결과**를 냅니다. 랭킹도, 응답 구조도 안 바뀝니다.
- "어느 영상인지 찾아줘"라는 의도를 감지해놓고 정렬에 반영하지 않습니다.
  (영상 단위로 점수를 합산해서 재정렬하는 식이 돼야 의미가 생깁니다.)
- 판정 사전도 역시 하드코딩 + `if` 순서 우선순위입니다:
  `SCENE_INTENT_TERMS` → `SUMMARY_INTENT_TERMS` → `VIDEO_INTENT_PATTERNS` → 기본 `scene`.

## 6. RAG 답변 (`search.py:213~258`)

상위 장면들을 `"1. [제목] 28.0초~32.0초 | 말: ... | 자막: ... | 장면: ..."` 형태로 이어
`ANSWER_PROMPT` 에 넣고 `gemini-3.5-flash-lite` 로 답을 만듭니다.
프롬프트에 "장면에 없는 내용은 지어내지 마 / 세 문장 안으로" 규칙이 있고,
호출이 실패하면 1등 장면의 시각을 그대로 문장으로 만들어 돌려줍니다(폴백).

## 8. 멘토에게 묻고 싶은 것

1. **가중치를 무엇으로 정해야 하나요?**
   지금은 감으로 쓴 값입니다. 평가셋 몇 개(질문–정답장면 쌍) 정도가 있어야
   Recall@5 / MRR 같은 지표로 그리드 서치를 돌릴 수 있을까요?
   졸업작품 규모에서 현실적인 최소 크기가 궁금합니다.

2. **질문 분류를 규칙에서 무엇으로 바꿔야 하나요?**
   (a) 사전 확장, (b) 소프트 분류(성격 점수를 섞어 가중치를 연속값으로),
   (c) LLM 분류, (d) 학습 기반 — 어느 정도가 적정한지.
   특히 "빨간 냄비에 간장 2큰술"처럼 **두 성격이 겹치는 질문**을 어떻게 다뤄야 할지.

3. **신호 융합 방식 — 가중합 vs RRF?**
   min-max 정규화 후 가중합은 스케일 문제가 있는데, RRF(순위 기반)로 바꾸면
   "가중치 튜닝"이라는 우리 기여 포인트가 흐려지지 않을까요?

4. **"관련 결과 없음"을 어떻게 판단하나요?**
   지금은 정규화 때문에 항상 1등이 나옵니다. 절대 유사도 임계값을 두는 게 맞는지.

5. **BGE-M3 / SigLIP2를 기본 경로에 넣는 게 맞나요?**
   지금은 비교 탭에서만 돕니다. 평소 검색은 Gemini embedding 2갈래로만 돕니다.
   심사에서 "3갈래 하이브리드"라고 말하려면 기본 경로에 넣어야 할 것 같은데,
   CPU 환경 응답 속도가 걱정입니다.

6. **lexical 신호를 BM25로 올릴 가치가 있나요?**
   한국어라 형태소 분석기(Kiwi/Mecab) 의존이 붙는데, 그만한 개선이 나올지.

## 9. 우리가 할 일 (아직 코드는 안 건드림 · 우선순위 순)

### 1순위 — 측정 기반부터 (이게 없으면 나머지는 전부 감입니다)
- [ ] **평가셋 만들기.** 저장된 영상들에 대해 `질문 → 정답 장면(video_id, 시각)` 30~50쌍.
      팀 4명이 10개씩 쓰면 하루면 됩니다.
- [ ] **평가 스크립트** `tools/eval_search.py` — Recall@1/@5, MRR 출력.
      기존 `tools/smoke_test.py` 가 이미 `weights_for` 를 부르고 있어서 붙이기 쉽습니다.

### 2순위 — 하드코딩 걷어내기 (실험 가능한 상태 만들기)
- [ ] `WEIGHTS` 를 **설정으로 분리** (`config.py` 또는 `weights.yaml`) → 재시작 없이 교체
- [ ] `POST /api/search` 에 **가중치 오버라이드 파라미터** 추가 → A/B를 API로 돌림
- [ ] 사전류(`VISUAL_TERMS` / intent 단어)를 별도 파일로 분리
- [ ] 매직넘버(`*8`, `10`, `5`, `4.0`)를 이름 있는 상수로

### 3순위 — 로직 개선 (2순위가 끝나면 효과를 숫자로 증명할 수 있음)
- [ ] **소프트 분류**: 하나만 고르지 말고 성격별 점수를 내서 가중치를 연속적으로 섞기
      → 겹치는 질문 해결. 이게 "우리가 설계했다"고 말할 수 있는 지점.
- [ ] **RRF 융합** 도입 후 가중합과 비교 측정 (둘 중 나은 쪽 채택, 근거는 평가셋)
- [ ] **lexical → BM25** (Kiwi 형태소) 로 교체하고 개선폭 측정
- [ ] **절대 임계값** 도입 → "저장된 장면에서는 확인되지 않습니다" 를 진짜로 판단
- [ ] **필드 가중치**: 제목/caption/asr/ocr 를 lexical에서 동일 취급하지 않기
- [ ] **intent를 랭킹에 반영**: `video` 의도면 영상 단위 점수 합산 후 재정렬

### 4순위 — 기본 경로 승격
- [ ] BGE-M3 / SigLIP2를 기본 검색에도 쓸지 결정 (속도 측정 후)
- [ ] `POST /api/search` 에 `condition` 파라미터 노출

### 심사 스토리로 쓸 것
> "가중치를 감으로 두지 않고, 평가셋 N쌍을 만들어 Recall@5 / MRR로 측정한 뒤
> 그리드 서치로 정했다. 규칙 기반 단일 분류를 소프트 분류로 바꿔 개선폭 X%를 얻었다."

개선을 해도 좋아졌다고 말할 근거가 없는 상태입니다.
