## 1. 종합 평가 — 유지할 것

멘토가 **적절하다고 평가한 판단들**입니다. 앞으로 설계를 바꿀 때 이것들은 건드리지 않습니다.

| 유지할 판단 | 자문 표현 |
| --- | --- |
| 검색 단위를 '영상'이 아니라 **'영상 속 장면'** 으로 설정 | "설정한 점 … 적절하다" |
| **요리 콘텐츠**로 적용 범위를 우선 축소 | "판단이 적절하다" |

| 검색 → 근거 제시 → 시점 이동까지 **파이프라인이 동작** | "동작하는 수준으로 구현되어" |

## 2. 보완 요구 5가지 — 무엇을 어디서 고치나

### 자문 1 · 장면 분할 단위

> 4초 고정 분할은 '재료를 볶는다', '불을 줄인다'와 같은 의미 단위(조리 단계)와 경계가 어긋나
> 하나의 행위가 여러 조각으로 흩어진다. **고정 분할을 기준선으로 두고, 인접 세그먼트를 의미
> 단위로 병합하는 후처리를 추가**할 것.

- **해당 코드**: [`segmenter.py:70`](../server/pipeline/segmenter.py#L70) `build_segments`, `SEGMENT_SECONDS=4.0`
- **할 일**: 4초 분할은 그대로 두고 그 **뒤에** 병합 단계를 붙입니다. 고정 분할을 없애지 않는 게
  포인트 — 멘토가 "기준선으로 두고"라고 명시했습니다.
- **주의**: 병합하면 세그먼트 경계가 바뀝니다. 그래서 평가셋 정답을 세그먼트 번호가 아니라
  **시간 구간(초)** 으로 적게 했습니다. 병합 전후 성능을 같은 평가셋으로 비교할 수 있습니다.

### 자문 2 · 신호별 역할 규명 ★ 핵심 기여

> 숏폼은 나레이션과 화면 자막이 중복되는 경우가 많고, 반대로 '색이 갈색이 될 때까지'처럼
> **시각 정보에만 존재하는 단서**도 있다. 질문 유형별로 어떤 신호가 유효한지 정리하면
> **그 자체가 본 프로젝트의 핵심 기여**가 된다. 세 신호를 모두 사용했다는 사실보다
> **각 신호의 필요성을 입증**하는 편이 설득력이 높다.

- **해당 코드**: [`search.py:19`](../server/search.py#L19) `WEIGHTS`, 응답의 `score_dense` / `score_lexical` / `score_image`
- **이것이 "어떤 모델에 가중치를 더 줄까"에 대한 답입니다.** 감으로 정하지 말고 유형별로
  측정해서 정하라는 뜻입니다. 측정 없이는 결정할 근거가 없습니다.
- **선행 조건**: 평가셋(4장). 이게 없으면 이 항목은 시작할 수 없습니다.
- 현행 가중치의 문제는 [`search-logic.md`](search-logic.md) 3장·7장에 정리돼 있습니다.

### 자문 3 · 근거의 신뢰성

> RAG 구조를 표방하는 이상 제시한 타임스탬프와 실제 장면이 일치해야 하며, 한 번 어긋나면
> 사용자 신뢰가 즉시 훼손된다. **근거가 불충분할 경우 답변을 생성하지 않고 '관련 장면 없음'을
> 안내하는 설계가 필요**하다(로드맵의 절대 유사도 임계값 도입 방향에 동의).

- **해당 코드**: [`search.py:69`](../server/search.py#L69) `minmax`, [`search.py:240`](../server/search.py#L240) `generate_answer`
- **지금 구조로는 불가능합니다.** min-max 정규화 때문에 각 후보 풀의 1등이 **항상 1.0점**이 되어,
  절대 유사도가 얼마든 상위 결과가 나옵니다. 원점수(cosine)를 보존하도록 먼저 고쳐야 합니다.
- **평가 방법과 연결**: 임계값이 제대로 도는지 보려면 **답이 없는 질문**이 평가셋에 있어야
  합니다. 그래서 전체의 10~15%를 "답 없음" 질문으로 만들기로 했습니다.

### 자문 4 · 처리 비용·지연

> 저장 영상 전체의 프레임에 캡션을 생성하는 구조는 서비스화 시 가장 먼저 부딪히는 제약이다.
> **영상 1건당 처리 시간과 비용을 실측해 자료에 명시**하면 '동작하는 데모'에서 '서비스 가능성이
> 있는 시스템'으로 평가가 달라진다.

- **해당 코드**: [`analyze.py:36`](../server/pipeline/analyze.py#L36) — `timings`가 이미 단계별로 수집되고
  `condition_runs` 표에 저장됩니다. **데이터는 이미 쌓이고 있고 집계만 하면 됩니다.**
- [`MENTOR_BRIEF.md`](MENTOR_BRIEF.md) 6-3에 영상 1개(81초) 실측표가 이미 있습니다.
  영상 수를 늘려 다시 재고, **비용(호출 수 × 단가)** 을 표에 추가하면 됩니다.
- 실제로 이 제약은 개발 중에 바로 터졌습니다 — 무료 티어 하루 20회 한도에 영상 5개에서 막혔고,
  영상당 호출을 4회 → 1회로 줄여 대응했습니다. **이 사건 자체가 자문 4의 근거 자료**입니다.

### 자문 5 · 저작권·이용약관

> 외부 플랫폼 콘텐츠의 추출·저장은 서비스화 시 약관 검토가 필요하므로, **현재 범위(개인 학습·
> 연구 목적)를 발표 자료에 명시**할 것.

- 코드 변경 없음. 발표 자료와 README에 한 단락 추가.
- 유리한 근거가 이미 설계에 있습니다: **서버는 유튜브에 한 번도 접속하지 않고**, 사용자가 자기
  브라우저에서 보고 있는 화면을 캡처해 올립니다([`MENTOR_BRIEF.md`](MENTOR_BRIEF.md) 1-2 원칙 1).
  yt-dlp 류 다운로드와는 성격이 다르다는 점을 같이 적습니다.

## 3. 평가 설계 — 멘토 지시 7가지

> 하나의 질의에 정답 장면이 복수일 수 있다는 지적은 타당하나, 이는 정보검색 분야에서 이미
> 다루는 문제이므로 **정성 평가로 이동하기 전에 정량 설계를 먼저 보완**할 것.

| # | 지시 | 반영 상태 |
| --- | --- | --- |
| 1 | 정답을 이진이 아닌 **등급(정확 2 / 관련 1 / 무관 0)** 으로 라벨링, **nDCG를 주지표**로 | 라벨링 시트에 반영 완료 |
| 2 | Recall@K·mAP은 **정답 집합을 복수로 확장**해 산출 | 한 질문에 여러 정답 구간을 적도록 설계 |
| 3 | 시점 정확도에 **비대칭 허용 오차** (예: 이전 5초, 이후 2초) | 평가 스크립트에서 구현 예정 |
| 4 | **질문 유형별**(재료·분량 / 순서·타이밍 / 시각적 상태)로 성능 분리 보고 | 라벨링 시트의 `q_type` 컬럼 |
| 5 | **비교 기준선** 설정 — 제목·설명 검색, ASR 단일 신호 대비 개선폭 | 평가 스크립트에서 구현 예정 |
| 6 | 평가셋 **편향 방지** — 2인 이상 독립 라벨링 + 일치도, 질문 작성은 팀 외부에 | 시트 [작성법] 탭에 절차 명시 |
| 7 | 정성 평가는 **소규모로**(10명 내외, 과제 성공률·소요 시간) — 만족도 설문보다 신뢰도 높음 | 평가셋 완료 후 |

### 비대칭 허용 오차의 판정 규칙

시스템이 안내한 시작 시각 `s`, 정답 구간 `[g_start, g_end]` 에 대해:

```
g_start - 5.0  ≤  s  ≤  g_start + 2.0     → 그 구간의 등급을 인정
```

> "사용자는 목표 장면보다 **앞서 시작하는 것은 감수하지만 지나쳐 시작하는 것은 감수하지
> 못한다**" — 현재 `SEEK_LEAD_SECONDS=1.5` (1.5초 일찍 이동)는 이 기준 안에 들어옵니다.

## 4. 평가셋 — 규모와 절차

**규모를 줄였습니다.** 저장 영상 전부에 질문을 만들 필요가 없습니다.

| | 개수 | 역할 |
| --- | --- | --- |
| 저장 영상 | 25개 | 검색 대상 전체 (난이도 유지) |
| 질문을 만들 영상 | **그중 12~15개** | |
| 질문 수 | 영상당 3~4개 = **45~55개** | 그중 5~8개는 "답 없음" |

질문을 안 만든 나머지 10개는 **오답 후보** 역할을 합니다. 검색은 25개 전체에서 도니까 난이도는
그대로인데 라벨링 부담만 절반이 됩니다.

**도구**: [`eval/labeling_sheet.xlsx`](../eval/labeling_sheet.xlsx) — 작성법 / 라벨링 / 영상목록 /
진행현황 4탭. 영상을 더 저장한 뒤에는 시트를 다시 만들면 [영상목록] 탭이 갱신됩니다:

```
python -m tools.make_labeling_sheet --force
```

## 6. 진행 순서

**1단계 · 지금 — 데이터 없이 되는 것**
- 평가 스크립트 골격 (nDCG · Recall@K · mAP · 비대칭 오차 · 유형별 분리 · 일치도)
- 기준선 2종 구현
- 합성 데이터로 스크립트 검증

**2단계 · 영상 25개 저장 후**
- 처리 시간·비용 실측표
- 라벨링 시트 재생성 → 질문 작성(외부) → 2인 독립 라벨링

**3단계 · 평가셋 도착 후**
- 현행 시스템 기준선 측정 (여기서 나온 숫자가 이후 모든 개선의 비교 대상)
- 절대 임계값 도입 → 재측정
- 인접 세그먼트 병합 → 재측정
- 신호별 기여도 측정 → 가중치 재설계 → 재측정

**4단계 · 마무리**
- 정성 평가 10명
- 추진 일정표·역할 분담표·저작권 범위 명시

## 7. 심사에서 말할 것

> "가중치를 감으로 두지 않았습니다. 질문 45~55개에 대해 등급형 정답을 2인이 독립 라벨링해
> (일치도 κ=0.XX) 평가셋을 만들고, nDCG를 주지표로 질문 유형별 성능을 분리 측정했습니다.
> 제목·설명 검색과 ASR 단일 신호를 기준선으로 두고 개선폭을 제시합니다."

**측정 → 개선 → 재측정 루프 자체가 기여입니다.** 자문 2가 말한 "세 신호를 모두 사용했다는
사실보다 각 신호의 필요성을 입증하는 편이 설득력이 높다"가 정확히 이 뜻입니다.
