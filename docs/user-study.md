## 자문이 요구한 것

> 1차(9/18): 정성 평가는 **소규모로**(10명 내외, **과제 성공률·소요 시간**) —
> 만족도 설문보다 신뢰도 높음.
>
> 2차(10/12): 처리 시간·비용 측정과 **사용자 평가로 서비스 가능성을 제시**하기 바람.

**방법까지 지정받았습니다.** 만족도 설문("유용했나요? 5점")은 쓰지 않습니다.
사람이 **실제로 과제를 해내는지**와 **얼마나 걸리는지**만 잽니다.

---

## 설계 판단 다섯 가지

### 1. 비교 대상을 "지금 하는 행동" 으로 잡았다

절대 수치만 내면 아무 말도 못 합니다. **"성공률 80%" 는 그 자체로 좋은지 나쁜지
알 수 없습니다.** 그래서 **사용자가 지금 실제로 하는 행동**과 비교합니다.

| A | 유튜브에서 **직접 스크롤**해 찾기 (대조군) |
| --- | --- |
| **B** | **검색창에 자기 말로 물어보기** (우리 시스템) |

우리 제품이 대체하려는 바로 그 행동이라, 여기서 이기면 **"쓸 이유가 있다"** 가
증명됩니다. 비슷하면 그것도 정직한 결과입니다. 이게 멘토가 말한 "서비스 가능성" 입니다.

### 2. 사람 안에서 비교한다 (within-subject)

10명을 두 그룹으로 나누면 **그룹 차이인지 도구 차이인지 알 수 없습니다.**
한 사람이 두 조건을 다 하되, **조건 순서와 세트 순서를 각각 5명씩 교차**해
학습 효과를 상쇄합니다.

**같은 과제를 두 조건으로 시키지 않습니다.** 두 번째는 답을 이미 알아 무의미합니다.
그래서 과제 6개를 3개씩 두 묶음으로 나눴습니다.

### 3. 검색어는 참가자가 직접 짓는다

질의문을 저희가 주면 **"그 질의가 잘 되는가" 만 재게 되고** 실제 사용과 멀어집니다.
**목표만 읽어주고 말은 본인이 고르게** 합니다.

> 덤: 참가자가 친 첫 질의문 30개는 **실제 사용자 말투**라 다음 평가셋 질문 재료가
> 됩니다(`docs/eval-guide.md`).

### 4. 성공 판정을 자동 평가와 같은 자로 한다

**정답 시작 기준 이전 5초 ~ 이후 2초.** `tools/eval_search.py` 의 `LEAD, LAG` 를
그대로 씁니다. 사람 평가와 자동 평가가 **같은 자**를 쓰게 하려는 것입니다.

판정은 **진행자가 하지 않고 엑셀이 합니다.** 도달 시점만 적으면 됩니다 —
사람이 암산하면 진행자마다 기준이 흔들립니다.

### 5. 제한 시간 3분

"소요 시간" 이 주지표인데 못 찾는 사람이 하나 있으면 평균이 무너집니다.
3분에서 끊고 실패로 기록해, **성공률**과 **성공한 과제의 평균 시간**을 따로 봅니다.

## 과제를 바꿀 때 지켜야 할 두 가지

`tools/make_user_study_sheet.py` 의 `check_tasks()` 가 **코드로 막습니다.**
어기면 생성 자체가 거부됩니다.

1. **정답이 영상 앞부분이면 안 됩니다 (12초 이상).** 허용 오차가 이전 5초라,
   정답이 5초면 인정 범위가 `0~7초` 가 되어 **영상을 건드리지 않아도 성공**이 됩니다.
   실제로 처음 고른 과제가 그랬고 뒤늦게 발견했습니다
2. **영상이 겹치면 안 됩니다.** 같은 영상이 두 번 나오면 참가자가 그 영상을 학습해
   두 번째 과제가 쉬워집니다

바꾼 뒤에는 **정답 구간이 `eval/labels_merged.csv` 에 라벨링돼 있는지** 확인하세요.
없으면 성공 판정을 할 수 없습니다.

## ⚠ 진행 전에 반드시 — AI 답변 생성을 끄세요

**검색할 때도 Gemini 를 씁니다.** 저장할 때만이 아닙니다.
사이드패널은 검색 한 번마다 `ANSWER_MODEL` 로 RAG 답변을 만들고, 이것도
**무료 티어 하루 20회**입니다.

```
참가자 10명 × B조건 3과제 × 검색어 1~3번 시도  =  30 ~ 90회  ≫  20회
```

**7번째 참가자쯤부터 답변이 안 나옵니다.** 진짜 문제는 답변이 없는 것이 아니라
**앞 참가자와 뒤 참가자가 다른 화면을 보게 되는 것**입니다. 그러면 비교가 깨집니다.

| | 방법 | 결과 |
| --- | --- | --- |
| **A (권장)** | 평가 기간 동안 **AI 답변을 끈다** | 10명 전원 동일 조건. 과제가 "장면으로 이동" 이라 답변은 평가 대상이 아닙니다 |
| B | 하루 **6명씩** 이틀로 나눠 진행 | 제품 그대로지만 날짜가 변수로 들어옵니다 |
| C | 그냥 진행 | **비교가 깨집니다. 권하지 않습니다** |

A 를 쓸 때 보고서 문장:

> 평가 중에는 RAG 답변 생성을 비활성화했다. 과제가 "장면으로 이동" 이고, 무료 티어
> 한도(모델당 하루 20회)로 인해 참가자마다 다른 화면을 보게 되는 것을 막기 위함이다.

## 참가자 조건

| | |
| --- | --- |
| 인원 | **10명** (멘토 지정 "10명 내외") |
| | **팀원 아님.** 이 프로젝트를 모르는 사람 |
| | 유튜브 쇼츠를 평소에 보는 사람 |
| | **과제 영상 6개를 본 적 없어야** 합니다 |
| | **질문을 만들어 준 지인과 겹치면 안 됩니다** — 그 사람은 영상 내용을 이미 압니다 |

개인정보는 **받지 않습니다.** `P01`~`P10` 으로만 기록하고 나이·성별도 묻지 않습니다
(분석에 쓰지 않을 것을 받으면 안 됩니다). 화면 녹화·녹음도 하지 않습니다.

시작 전에 **"언제든 중단할 수 있다"** 와 **"참가자가 아니라 시스템을 평가하는 것"**
을 말로 알립니다. 뒤엣것을 미리 말해두면 행동이 자연스러워집니다.

## 결과를 어떻게 보고하는가

### 주 표

| | A 직접 찾기 | B 우리 시스템 |
| --- | ---: | ---: |
| 과제 성공률 | __ / 30 | __ / 30 |
| 성공한 과제의 평균 소요 시간 | __ 초 | __ 초 |
| 평균 시도 횟수 | __ | __ |

유형별(재료·분량 / 순서·타이밍 / 시각적 상태)로도 같이 냅니다 —
유형별 성능 차이를 이미 측정해 뒀기 때문입니다(`PROGRESS.md` 5-2장).

### 이 설계로 낼 수 있는 정밀도 — 미리 알아야 합니다

조건당 과제가 30개뿐이라 **신뢰구간이 넓습니다.**

| 성공 | 성공률 | 95% 신뢰구간 | 폭 |
| ---: | ---: | --- | ---: |
| 18/30 | 60% | 42% ~ 75% | 33%p |
| 21/30 | 70% | 52% ~ 83% | 31%p |
| 24/30 | 80% | 63% ~ 90% | 28%p |
| 27/30 | 90% | 74% ~ 97% | 22%p |

**두 조건의 구간이 겹치지 않으려면 30%p 이상 차이**가 나야 합니다 —
A 가 60% 면 B 가 **93% 이상**이어야 "확실히 다르다" 고 말할 수 있습니다.

소요 시간도 같습니다. 사람마다 편차가 평균의 50% 정도면 **40% 이상** 차이나야
구분됩니다(쌍체 t, 참가자 10명, 검정력 80%).

> **이건 설계 결함이 아닙니다.** 멘토가 "소규모(10명 내외)" 로 지정했고, 소규모
> 평가는 **큰 차이만 잡습니다.** 작은 차이를 재려면 수십 명이 필요한데 졸작 범위를
> 넘습니다. 한계를 알고 그 선 안에서 말하면 됩니다.

### 가장 강한 수치는 "10명 중 몇 명"

참가자마다 A 3과제와 B 3과제를 비교하면 **10쌍**이 생깁니다. 이게 사람 안에서
비교한 설계의 핵심이고, 전체 평균보다 설득력이 있습니다.

| 조건 | 부호검정 |
| --- | --- |
| 10명 중 **9명 이상**에서 B 가 나음 | p = 0.021 (유의) |
| 무승부 1명 빼고 9명 중 **8명** | p = 0.039 (유의) |

**"10명 중 9명이 제안 시스템에서 더 빨리 찾았다"** 가 평균 비교보다 쓰기 쉽고
강합니다. 평가지에 참가자별로 기록되므로 그대로 셀 수 있습니다.

### 지킬 것

- **n=10 입니다.** 조건당 30과제뿐이라 **"유의하게 높다" 는 쓰지 마세요.**
  "73% 대 90% 였다" 까지만 씁니다
- 시간 비교는 **성공한 과제만**. 실패를 180초로 넣으면 왜곡됩니다. 실패 건수는 따로 밝힙니다
- 불편 의견은 **인용만** 하고 세지 마세요 (만족도 설문을 하지 말라는 것이 자문의 취지)
- **"2배 빨랐다" 같은 표현을 쓰지 마세요.** 성공한 과제만 평균 낸 값이라 과장됩니다

### 서비스 가능성으로 연결하기

멘토가 요구한 것은 "서비스 가능성 제시" 입니다. **처리 시간·비용 실측**
(`PROGRESS.md` 5-3장)과 붙여 쓰면 답이 됩니다:

> 영상 1건 저장에 캡처 47초 + 서버 110초가 들고 하루 20건이 한계다(**비용**).
> 그 대가로 사용자는 장면 찾기를 __초에서 __초로 줄였다(**효용**).
